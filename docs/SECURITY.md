# Security and privacy

## Hard guarantees

1. **No automatic remediation.** No block, isolation, account change or firewall change exists anywhere in the code.
   Recommendations carry `display_only: true, automated: false`; a test scans the playbook handlers, the provider adapters
   (no PUT/PATCH/DELETE, no OpenCTI mutations) and the whole backend (no `subprocess`, `os.system`, `eval`, `exec`).
2. **Nothing from an incident is executed.** Commands are analysed as text; encoded PowerShell is decoded for inspection only.
3. **Sensitive data stays local.** Private, internal, loopback, link-local and documentation addresses, internal domains and
   e-mail addresses are never sent to public CTI providers. External LLMs only receive pseudonymised data and only if explicitly
   enabled. Local Ollama never leaves the host.
4. **Read-only integrations.** CTI lookups, bucket downloads and OpenCTI queries only read.

## Controls

| Area | Implementation |
|---|---|
| Authentication | `X-API-Key` (constant-time comparison); keys in `API_KEYS`, generated by the start scripts. The dashboard calls the API through a server-side proxy so the key never reaches the browser |
| Input validation | Strict Pydantic schema (`extra=forbid`, length/range limits, timezone-aware timestamps, ≤ 200 indicators), safe JSON parsing |
| Limits | Request body ≤ 256 KiB (413); 120 requests/min per key (429); provider timeouts, retries with backoff |
| Secrets | `.env` git-ignored; credentials entered in the UI are Fernet-encrypted (key derived from `SECRET_KEY`) and write-only through the API |
| Audit | `audit_logs`: incident submissions, credential changes, syncs (actor = key fingerprint, client IP) |
| Prompt injection | Pattern scan, neutralisation, delimited untrusted blocks, evidence-ID validation, capped AI influence (see AI_AGENT.md) |
| Provenance | Every CTI result stores provider, time, status, data origin (`live`/`cache`/`demo_fixture`), raw response |
| Transport hygiene | `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`; CORS restricted to `CORS_ORIGINS`; containers run as a non-root user |
| Persistence | Alembic migrations, PostgreSQL volumes; stale jobs recovered with a heartbeat |

## Bucket artifacts (models are pickles)

Loading a model file executes code, so remote artifacts (`gs://`, `hf://`) are loaded only if the **HMAC-SHA256 signature**
(`ARTIFACT_SIGNING_KEY`, shared with the publisher) and every file's **sha256** verify; a missing key is refused. Versions are
validated against path traversal and installed atomically after verification. Use a **read-only** service account for Sfumato
(`roles/storage.objectViewer`) and a separate write-capable one for the trainer. Keep the signing key out of the bucket.

## Known limitations (be honest in the review)

* One shared API key model: no users, roles or per-user audit. Fine for a single-team demo, not for production.
* **No TLS** out of the box: put a reverse proxy with HTTPS in front before exposing anything beyond localhost.
* The default development key `sfumato-dev-key-change-me` is used when `.env` is absent (the start scripts replace it).
* The SSE stream is excluded from the rate limit.
* Prompt-injection defences are mitigations, not proofs; the evidence-validation and capped-influence design is what limits damage.
* The local Ollama path sends data unredacted (it stays on the host).
* Dependencies are pinned but not audited for CVEs here (`pip-audit`, `npm audit` are not part of the test suite).
* Docker images, the real GCS bucket and OpenCTI FULL mode have not been security-reviewed in a running deployment.

## Cloud VM deployment (docs/GCP_DEPLOYMENT.md)

Caddy terminates TLS and requires a team login; the dashboard and API listen on localhost only. The deploy package is
verified by sha256 (kept in instance metadata) before it runs. Secrets travel in instance metadata, not in the bucket.
Remaining exposure: SSH is open through GCP default rules, the login is a shared basic-auth password per person with no
rate limiting in Caddy, and the free Gemini tier may use prompts to improve Google products.

## Hardening checklist

Set strong `API_KEYS`/`SECRET_KEY`/`POSTGRES_PASSWORD`; do not publish ports 5432/6379/8000 beyond localhost; terminate TLS in a
proxy; restrict `CORS_ORIGINS`; keep `AI_ALLOW_EXTERNAL=false` unless needed; rotate the bucket keys; run `pip-audit` and `npm audit`.
